Chapter 3: Methodology
3.1 Introduction
This chapter outlines the methods used for the design, development and training of the Ruzivo text based conversational AI system. The study followed the Design Science Research (DSR) methodology described by Baskerville et al. [5] which describes the DSR cycle: definition, design and development, construction, evaluation, and design revision. The chapter explains the hardware and software configuration, the architecture of the proposed system, data collection and data pre-processing methods, decision of algorithms and models, and the results of training the validity of the models and checking the function. If there have been any deviations in the implementation from initial design decisions (because they were not compatible with the existing libraries, hardware limitations, or the experience gained in the development process) they are described, together with the technical reasons, as they make a contribution of their own kind and become a finding of the research, whose methodological contribution is addressed by the collection of findings.
3.2 Hardware and Software Requirements
3.2.1 Hardware Requirements
The Ruzivo system was built and integrated in three different hardware environments, targeting specific roles for a development life cycle.
This is a consumer notebook with 5.6 Gb of total memory, all of which was allocated to the Linux subsystem (in the form of a Windows Subsystem for Linux 2 (WSL2) instance of Ubuntu 24.04). All CPU based model predictions were performed in this environment, along with the FastAPI backend server [24] and the service for PostgreSQL and Redis as well as the Expo frontend development server (backend React Native). Being deployed on a non-GPU machine, all local inferences saturated the CPU resulting in the values of the response latencies being in the range of 60-90 seconds per generation, as documented and covered in the lazy model loading process to avoid delays on the application start.
All coding and training of models were done on Kaggle Notebooks, offering access to NVIDIA Tesla T4 GPUs with 16GB of GPU memory, at no cost. The selection of the T4 GPU (Turing architecture, compute capability sm_75) was made for training. In order to avoid crashing from PyTorch [23] builds lacking support for sm_60, the alternative version of the P100 GPU, which does support sm_60, was used as was confirmed on Kaggle. If device_map=”auto” the model is allocated across all available GPU's, so the training runs were set on a single GPU (os.environ[“CUDA_VISIBLE_DEVICES”]”0”). This ensured that the model fit on a single GPU and made checkpointing/loading easier.
The Hugging face Hub was used to set-up model and dataset storage—a layer of persistent storage while working in the Kaggle training space and deploying to WSL. It is established as a three-tier hardware architecture with an application of WSL for development and inference, Kaggle for training, and Hugging Face Hub for storage, which was required by the “free-tier” limitations faced by all platforms and which represented an application of the methodology applicable to other researchers under similar resource constraints.

The Ruzivo system was completely developed using open-source system software. The backend also used Python 3.11 with the web framework FastAPI [24], SQLAlchemy as ORM [26] and PostgreSQL database [25] along with Redis as cache and session store [27]. Frontend was developed with Expo SDK 56 (React Native) and React Navigation (for screening) and Axios (for API interaction).

3.3 Proposed System Architecture
The Ruzivo system is designed as five layers each consisting of a separate service; the client, the API gateway, the service or application, the model and the data. The proposed system architecture is shown in figure 3.1.
The client layer is a React Native Expo app that provides a single codebase and delivers a consistent Shona-language text-based conversational interface to Android, iOS and Web. The client only interacts with their back end API via HTTP REST, sending text messages and/or file uploads, and receiving text responses. The client only communicates with their back end API via HTTP REST, sending text messages and file uploads, and receiving text responses.
The API gateway layer consists of FastAPI application [24] running on port (5000). It includes three main router modules: /auth provides functionality for registering your user and JWT authentication, /chat allows you to have text conversations with the user, and /files allows you to upload documents and texts. All endpoints apply a Shona-language constraint via a common language detection service which returns a consistent Shona-language error message when an input is not Shona language.
The service layer consists of two independent and loadable service singletons: LLMService (Qwen2.5-1.5B [12] + QLoRA adapter [6]) and RAGService (FAISS index [15] + LaBSE embeddings [17]). Each function has a load() routine that is fired when the application starts using the FastAPI's lifespan context management. The LLMService also supports lazy loading in that the _load() method is only called the first time generate() is called, meaning that /health will respond as soon as the service starts and not be stalled on the first call while the model is being initialised (60-90 seconds).
The data layer includes a PostgreSQL relational database that contains user accounts, conversation histories and message records, a Redis cache for session management and rate limiting, and a Hugging Face Hub dataset repository that hosts the FAISS vector index (shona_labse.index, 98,993 vectors, 768 dimensions) and sentence corpus (sentences.json) employed by the RAG pipeline.
The collected data has been pre-processed for this model. This model is based on pre-processed data.

3.4 Data Collection and Preprocessing
3.4.1 Text Corpus Construction
The Ruzivo text corpus was compiled from four existing (publicly available) sources of Shona language texts. The Google FLEURS Shona dataset (sn_zw) [20] is the source of 3,781 text transcriptions of read speech based on content from Wikipedia articles, in the form of encyclopedic sentences, which are highly orthographically consistent and based on facts. The sentences of formal religious prose in standard written Shona were taken from the Shona Bible, which was retrieved from publicly available electronic text. The Shona Bible, retrieved from public electronic text, was used for the 31,029 sentences of formal religious prose in standard written Shona. The Shona Wikipedia dump produced 82,707 sentences of encyclopedic information for various factual areas. The contemporary journalistic prose was made up of 124 sentences provided by the Nehanda Radio Shona news archive. Finally, a clean corpus was built with 98,993 sentences, after deduplication and sentence-level quality filtering, stored in the JSON format (UTF-8 encoded).
A frequency-threshold English word detection audit of the corpus showed previously that about 4,132 sentences (4.2%) had majority-English content, mainly as a result of bilingual glossary giving, from the un�� Wikipedia dump. The entries that remained in the corpus were those that included Shona vocabulary definitions and not noise, hence removing these entries would have reduced the model's domain knowledge without any improvement to the entries. English was carried out by subtracting the 300- or more frequent words from the Shona verified corpus from a 370,111-entry English word list, which preserved Shona words also having orthographic form in the English list: for example, 'apa' (here), 'here' (the Shona question particle), 'rake' (his/her).
3.4.2 Training Data Construction
To facilitate the supervised fine-tuning corpus and to ensure that the distribution of the corpus during training closely resembled that of the prompts during the inference time of the deployed system, the corpus was broken into four well-labeled sub-corpora.
The two Shona instruction templates, namely "Tsanangura izvi muShona: {text}" and "Rondedzera izvi muShona: {text}" were used to create two instruction-response pairs for each of the 98,993 corpus sentences whereby the actual sentence content was replaced by {text}. This yielded 197,986 instances which sustained the model with Shona patterns. In this construction pass a critical defect was found and fixed - the original training corpus had no '{text}' representative for instructions, so in 33,000 or so instances, it had a fixed sequence of instructions with randomly varying output sequences.
The Slang and conversational register segment is comprised of the Shona Slang dataset [21] cleaned with the English detection algorithm described in Section 3.4.1 performed on the corpus. Messages composed of four or more words with zero residual English-dictionary words were kept, resulting in 4,438 clean informal Shona messages produced by the method in pairs of instruction—response. This segment was used to expose the model to the spontaneous (natural) register of the language of focus, Shona, which was not used in the formal sources that were used in Segments 1 and 3.
Thirty-two pairs of instruction-response statements for the greeting, thanking, identity, capability and farewelling intents were curated with native shona speakers and over-sampled by 2500, resulting in 80000 items. This part discussed the lack of examples of conversational input in the original corpus data, which had led to a tendency of previous model releases to generate formal, non-conversational output for informal conversational language input.
To support that, LaBSE was used to encode a random sample of 5,000 sentences from the corpus and the top-3 nearest neighbour to each sentence in the FAISS index [15] was retrieved. All of the sample sentences were encoded in the format of a query-response pair, as follows, to mimic the question and response that would be presented at the time of inference: "### Context:\n{retrieved_sentences}\n\n### Instruction:\n{instruction}\n\n### Response:\n{answer}". This used to be an issue in previous versions of the model, and now in this version, a context injection failure search task is taken care of by feeding the context to the model and appending it to the prompt to ensure that the instruction gets echoed.
After random shuffling, the final combined corpus consisted of 212824 examples – 191541 were used to train the model and 21283 were used as a test sample. Corpus files were saved in JSONL format and put in the dataset repository on Hugging Face Hub cybux/ruzivo-shona-rag.

3.5 Algorithm Design
3.5.1 Language Detection Algorithm
Added Shona language detection to enforce system's Shona only constraint at the system boundary using 'light' approach that accepts keywords. There is an intimate repertoire of 39 high-frequency marker words and morphemes – such as common pronouns – ndi, iwe, isu – and discourse particles kuti, kana, asi, uye – and greetings mhoro, maswera – and question words chii, sei – among these. There is whitespace-based tokenisation and a match is recorded if any marker is a sub-string of any token. Machine-generated texts that return at least one marker match are then categorized as Shona texts and sent to the inference pipeline, in addition to the texts with 3 or fewer words. There is no rejection language in Shona for non-Shona inputs, but rather a standardisation response in Shona without invoking the rejection LLM and/or RAG pipeline.
This approach is chosen on the grounds of execution having zero latency and shoes zero dependency footprint. While a full language identification model, like the model supplied by fastText (lid.176.bin), was considered, it would impose an additional model loading step in the system start sequential, and also add a classification latency for each request that would sadly not profit the detection effort much for the small conversational input this system is expected to receive.
3.5.2 Retrieval-Augmented Generation Algorithm
The RAG pipeline [8] works as below: When loading, the RAGService singleton fetches the FAISS index (shona_labse.index, 98,993 vectors with 768 dimensions) from the Hugging Face Hub dataset repository as well as the sentence embedding model (LaBSE) and the sentence corpus (sentences.json). The user's query is embedded at inference time as a 768-dimensional L2-normalised vector using LaBSE, with normalize_embeddings=True. FAISS IndexFlatIP gives exact results for inner-product search, which is same as cosine similarity in L2 norm of normalised vectors, and provides top-5 kNNs and similarity scores. Scores above 0.5 are considered relevant information for the LLM prompt and then combined at the end to form the context. If the result of this is below threshold, it is set to null, and the LLM is called without context.
An empirical validation of the embedding model selection was carried out. The first model deployed, paraphrase-multilingual-MiniLM-L12-v2 [16], was observed to hold up semantically unrelated answers for Shona queries with high cosine similarity of over 0.85. It was established through investigation that this was due to the lack of the language in the model published list of training languages in the sub-Saharan African region. A self-search sanity check was carried out, where 10 random sentences that were part of the corpus were each encoded and then queried against the FAISS index using k=1 as query (no self-exclusion). The highest index construction score, with cosine similarity of 1.0000, came from all ten, who returned the original sentence back to the question. So the inflated scores could only be due to model quality rather than indexing errors done. After verifying that it is an explicit Shona language (language code sn), laBSE was chosen as its replacement by confirming that it handles 109 different training languages and was empirically validated to achieve good retrieval quality in failure queries as well as positive control queries. Thus, the index was reconstructed with 768 dimensions to match the number of dimensions output by LaBSE.
PILOT algorithm for the fine-tuning of the Shona Language Model.3.5.3 Shona Language Model Fine-Tuning Algorithm.
The fine-tuning process for the language model was done using QLoRA [6] on the base model Qwen2.5-1.5B [12]. All attention layers had low-rank adapter matrices with r = 16 and α = 32 for query projection (q_proj), key projection (k_proj), value projection (v_proj) and output projection (o_proj). All other base model weights were held frozen while only 4,358,144 adapter parameters were updated on the basis of the gradients (0.28% of all the parameters) This setup allowed the entire fine-tuning process to be finished with a single Kaggle T4 GPU after about 2.5 hours per fine-tuning iteration.
The SFTTrainer Class from the SFT Library was used to provide the training, and then used in conjunction with the SFTConfig configuration object. During implementation an API compatibility was built which revealed deprecation of dataset_text_field and max_seq_length arguments in TrainingArguments class, into SFTConfig. Furthermore, the TrainingArguments parameter torch_dtype was silently ignored in favor of the correct parameter dtype and the base model would load in float32 instead of float16, using about double the desired RAM. These problems were both discovered and solved prior to the last practices.

3.6 Model Design
3.6.1 Language Model
The Ruzivo language model was developed using the Qwen2.5-1.5B [12] and implementing it as a QLoRA version. The whole model was loaded in float16 precision with PyTorch [23] to keep the memory usage low, and the QLoRA adapter was applied with PEFT library's peftmodel from pretrained interface, peft_model from pretrained [6]. The model uses sampling with top_p = 0.9 and temperature = 0.7 at inference which was empirically determined to lead to more varied, natural sounding Shona text than greedy sampling. The maximum number of tokens per generation was fixed at 80 per generation, which is enough to keep conversational interactions from getting out of hand, but isn't so big that they create a lot of "jams.
Implements lazy loading : the _load() method is called only the first time generate() is called; the FastAPI /health endpoint will reply immediately when it starts up because it doesn't wait on the 60-90 second that the model takes to initialise. A public load() method is supplied to satisfy the lifespan contract for using the context manager in main.py, including service.load(), which is called for each registered service on start-up, in this case, a public method.
It appeared a training collapse occurred in the first fine tuning run (data: cybux/ruzivo-shona-llm, version: v1). A save_total_limit=2 configuration (which caused the machine to delete all checkpoints except for the two most recent ones) combined with a Kaggle session restart at training step 3,600 led to excision of the last known good checkpoint (called checkpoint-800), which was seen at 62.38% token accuracy. Greedy decoding revealed the surviving checkpoint-3600 gave degenerate outputs with any input. This was methodologically recorded and used to design a preservation strategy for all subsequent training runs: save_total_limit=10, and a hub strategy="checkpoint" with checkpoint saving every 200 steps, coinciding every 200 steps even with no continuity sessions.

3.7.1 Language Model Training Results
The Ruzivo language model was trained with five training runs that resulted in the iterative improvement of the training corpus and the conversational ability of the trained model. Details about the training runs are summarised in Table 3.5.
However, because of the interruption of a Kaggle session and the use of configuration save_total_limit=2, that should have erased the last known-good checkpoint (as originally described in Section 3.6.1), v1 failed to recover. Version 2 (v2) was trained successfully to 1000 steps on the original training corpus which contained the uncorrected Template 1 placeholder bug and no conversational training examples. The grammatically more accurate automatic generation of Shona text by the model was not accompanied by it being able to succumb to identity or capability or conversational prompts, and it hallucinates when set factual ones.
Version 3 (v3) was trained on the corrected 4-segment corpus described in Section 3.4.2, and it obtained a final token accuracy of 72.1 % – a 10.2 % improvement over v2. The model gave very good answers to identity and greeting requests, as well as responding to most conversational questions. The version 4 (v4) was trained using an aggressively rebalanced corpus with 5000x conversational 2s, reporting an accuracy rate of 85.9% at the level of tokens. It was later revealed that this score was skewed—the model was essentially memorizing the 33 conversational pair templates and their responses and started to perform very well on them but not at all on knowledge-based prompts. Version 5 (v5) was trained using a rebalanced corpus that includes 2,500 times more conversational pairs than a rebalanced sample of plain-grounded examples from the same test set, plus 50,000 examples and 40,000 context-augmented examples, resulting in a token accuracy of 71.4%, with better generalisation for conversational and knowledge query categories.
3.7.2 RAG Validation Results
In order to validate the RAG pipeline [8] the self-search sanity check method [17] was used to encode 10 different sentences from the corpus using LaBSE [17] and then to search for them with the index created by the RAG pipeline [8] with k = 1 and self-excluding = false. All 10 queries were matched with the sentence, with cosine similarity being 1.0000 which indicates that all three parts – the construction of the index, the L2 norm and the aligning of sentences and index – are correct. It was observed that the stored vector norms were all equal to 1.0, which was the desired result.
The questions for this study were carefully selected. Three queries that are particularly challenging were used for the qualitative retrieval evaluation which included the Shona ideophone "gojoto", metal alloys (musanganiswa wesimbi), leprosy (hosha yamaperembudzi), and the original MiniLM embedding model [16]. The three gave answers that had nothing to do with each other, but had cosine similarities larger than 0.85. For good Shona representation in embedding (well-represented topics) launching queries with positive control seemed to return meaningful similarity signals with LaBSE, whereas with MiniLM launching queries seemed to return it with high confidence even for non-sentimentally relevant results.
3.8 Summary
The entire process of the Ruzivo project was detailed in this chapter. An easy-to-implement method was proposed that does not incur any cost for computation, particularly in free-tier research setting, in academia: use the processors for inference, use the Kaggle T4 GPU for training and persistent storage, and use the Hugging Face Hub for persistent storage [23]. The multiple layers of service-oriented system architecture were introduced, starting from the client side, the API gateway, the service layer, the model layer, and the data layer; The LLM and RAG service singletons are loaded independently; The language constraint is placed on the API level. Data collection and preprocessing procedures were used for the creation of a Shona text corpus consisting of 98,993 sentences taken from the FLEURS dataset [20] in addition to the Bible, Wikipedia and Nehanda Radio and a fine-tuning corpus of 4 segments with a total of 287,424 examples, but including examples representing plain-grounded, slang, and curated conversational text, and context-augmented training examples. The RAG algorithm design documented the case study data-driven switch from MiniLM [16] to LaBSE [17] due to self-search empirical experiments, and the fine-tuning configuration of QLoRA [6] was completely argued regarding all the hyper-parameters. Five iterative training runs were presented and the accuracy of the tokens and the accuracy of the conversational responses for all the categories of identity, greeting and capability tested for the production model v5 was 71.4%.
The evaluations of the end-to-end system is summarized in Chapter 4, along with comparative evaluations of the different versions of the model, morphological competence testing, evaluations against the BLEU score to the shifts in end-to-end system performance with the introduction of the BLEU score to a new model version (Qwen2.5-1.5B), and evaluations relative to the human assessment of the performance of a native Shona speaker.
